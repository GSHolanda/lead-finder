## 3. Requisitos originais (resumo fiel do pedido do usuário)

### Descoberta

- Buscar por localização e segmento com fontes gratuitas.
- Priorizar quem tem o campo de site vazio ou só redes sociais, agregadores, delivery ou WhatsApp.
- Não descartar nem concluir "sem site" antes da verificação.

### Verificação de site

- Usar:
  - links dos registros;
  - busca por nome + cidade/bairro;
  - telefone e endereço, para distinguir homônimos;
  - perfis públicos, quando acessíveis e permitidos;
  - confirmação manual.
- Classificações:
  1. Site próprio encontrado.
  2. Somente redes sociais ou plataformas.
  3. Site próprio não localizado após verificação.
  4. Verificação inconclusiva.
  5. Possível site indisponível.
- Registrar consultas, fontes, data e confiança.
- **Falha de consulta ≠ ausência de site. Domínio fora do ar ≠ ausência de site. Não associar site só por semelhança de nome.**
- Permitir correção manual, preservar o histórico e nunca sobrescrever correções humanas.

### Pesquisa sem site

- Não depender de site próprio. Usar fontes de descoberta, perfis, redes, diretórios e materiais do usuário.
- Coletar só o que for comprovável:
  - nome comercial;
  - segmento e serviços;
  - região atendida;
  - contato comercial;
  - redes sociais;
  - forma de contratação;
  - evidências para a proposta.
- Não exigir login, não contornar bloqueios, não inventar.

### Qualificação

- Combinar:
  - site não localizado com verificação suficiente;
  - aderência ao serviço;
  - contato disponível;
  - benefício plausível e específico;
  - qualidade das evidências.
- Não presumir faturamento, orçamento, interesse, perda de clientes ou falta de profissionalismo.
- Empresas com site encontrado vão para uma lista separada, fora da campanha.

### Abordagem

- Mensagens fundamentadas no que foi encontrado.
- Se a ausência de site não foi confirmada pela empresa, perguntar "Vocês já têm um site próprio?".
- Sem críticas, sem promessas de vendas ou Google, sem fingir projeto, análise ou proposta.

### Interface (para cada empresa)

- classificação de site;
- confiança e fontes;
- contato;
- resumo do negócio;
- possível aplicação de um site;
- mensagem editável;
- próxima ação.

### Piloto

- Revisar manualmente uma amostra dos "site próprio não localizado".
- Medir quantos tinham site.
- Melhorar a verificação antes de aumentar o volume.

## 4. Arquitetura

Só Python 3.10+, biblioteca padrão, **sem dependências**. Banco SQLite em `data/leadfinder.db` (ou `$LEADFINDER_DB`). Interface web local em `127.0.0.1:8765`.

| Arquivo | Responsabilidade |
|---|---|
| `leadfinder/db.py` | Esquema SQLite e `add_history`. A classificação automática (`site_status_auto…`) e a manual (`site_status_manual…`) ficam em colunas separadas. |
| `leadfinder/statuses.py` | Classificações, rótulos, origens de correção e funil. `effective_status` = manual se existir; senão automática. |
| `leadfinder/normalize.py` | Telefones BR (comparação por DDD + últimos 8 dígitos), CNPJ, CEP, e-mail. Nome por termos distintivos (`GENERIC_WORDS`). |
| `leadfinder/urls.py` | Classifica links: próprio, site em plataforma, rede social, WhatsApp, agregador, delivery, agendamento, marketplace, diretório, encurtador, não relacionado. Também `email_domain`. |
| `leadfinder/net.py` | `HttpClient` com robots.txt (RFC 9309), intervalo por host, limite de bytes e classificação de falhas. Não contorna 401/403/429. |
| `leadfinder/config.py` | Configurações salvas na tabela `settings`. A chave Brave aparece mascarada. |
| `leadfinder/leads.py` | `LeadRecord`, `upsert_record` e `add_link`. Deduplicação: fonte → CNPJ → telefone + termo distintivo comum → nome + bairro/cidade. Calcula a prioridade de descoberta. |
| `leadfinder/discovery/osm.py` | Overpass/Nominatim: DF inteiro, Região Administrativa por raio e municípios de GO. A tag `brand` marca possível rede/franquia. |
| `leadfinder/discovery/importers.py` | CSV genérico e arquivo de Estabelecimentos do CNPJ. Só ativos com nome fantasia; Brasília = 9701. |
| `leadfinder/discovery/segments.py` | 19 segmentos: tags OSM, prefixos CNAE e benefícios típicos. |
| `leadfinder/discovery/regions.py` | Regiões Administrativas do DF e municípios do entorno em GO. |
| `leadfinder/verification/search.py` | Provedores: SearXNG local, Brave ou nenhum. Consultas e links de busca manual. Não raspa o Google. |
| `leadfinder/verification/page.py` | Lê HTML e compara evidências: forte (telefone, CNPJ, e-mail), média (CEP, endereço), fraca (nome). Detecta diretórios e domínios estacionados. |
| `leadfinder/verification/verifier.py` | **Núcleo**: etapas de verificação, avaliação de candidatos e decisão (ver seção 5). |
| `leadfinder/verification/manual.py` | Correções humanas, flag de rede/franquia e funil, sempre com histórico. |
| `leadfinder/ollama.py` | Cliente do Ollama: `/api/chat`, saída estruturada e lista de modelos. |
| `leadfinder/enrichment.py` | Fatos estruturados mais extração por Ollama, **validada por trecho literal**. Fatos rejeitados pelo usuário não voltam. Resumo factual. |
| `leadfinder/qualification.py` | Pontuação 0–100 (35/20/20/15/10), benefícios com evidência, melhor contato, próxima ação e exclusões. |
| `leadfinder/outreach.py` | Mensagem por modelo padrão ou Ollama, regras de bloqueio (`check_guardrails`), versões, edição e aprovação. |
| `leadfinder/pilot.py` | Amostra, revisão, relatório (IC de Wilson, recortes, diagnóstico de erros, decisão de escalar) e reverificação. |
| `leadfinder/service.py` | Ligação entre os módulos: `process_lead`, `list_leads` (views campanha/verificar/com_site/todos) e `lead_detail`. |
| `leadfinder/server.py` | Servidor HTTP com API JSON e fila de tarefas. POST exige JSON e mesma origem. |
| `leadfinder/static/` | Interface em vanilla JS: abas Campanha, A verificar, Com site, Todos, Descoberta, Piloto e Configurações. |
| `leadfinder/cli.py` | Comandos: `serve`, `descobrir`, `importar-csv`, `importar-cnpj`, `processar`, `corrigir-site`, `listar`, `piloto-*`, `config`, `exportar`. |
| `tests/` | `fakes.py` (cliente HTTP, busca e Ollama simulados), mais `test_verifier`, `test_analysis`, `test_sources`, `test_server` e `test_net`. |

## 5. Lógica de verificação (`verifier.py`)

### Etapas

1. Links dos registros com associação `fonte`, `agregador` ou `usuario`:
   - encurtadores são resolvidos;
   - domínios próprios são acessados;
   - agregadores são lidos (com robots) e seus links de saída entram na fila;
   - redes sociais não são lidas (exigem login) e ficam registradas como presença.
2. Domínio do e-mail, se não for provedor gratuito. Quando o e-mail vem do CNPJ, a associação é `email_cnpj`: pode ser o domínio do contador, então exige o nome da empresa no site.
3. Busca: até 3 consultas (nome + cidade, nome + bairro, telefone) e até 5 candidatos por domínio.
4. Domínios prováveis (`slug.com.br`, `slug.com`), só se nada foi confirmado. Aceitos apenas com evidência.

### Avaliação de cada candidato (`evaluate_site`)

Resultados possíveis:

| Resultado | Quando |
|---|---|
| `confirmado` | evidência forte, ou média + nome |
| `existe` | associação forte, sem contradição no conteúdo |
| `bloqueado` | robots/401/403/429 — não contornado |
| `indisponivel` | o site não respondeu normalmente |
| `estacionado` | domínio estacionado ou página padrão |
| `redireciona` | redireciona para rede social etc. |
| `diretorio` | mais de 6 telefones distintos ou marcadores de guia |
| `so_nome` | só o nome confere, com menção à região |
| `homonimo` | só o nome confere, sem menção à região |
| `sem_relacao` | nada confere |
| `nao_corresponde` | conteúdo contradiz o lead |
| `nao_conferido` | não foi possível conferir |
| `confirmado_trecho` | confirmado pelo trecho do resultado de busca |
| `erro` | outra falha |

### Decisão (`_decide`), em ordem

1. Algum `confirmado` → **site_proprio** (0,95 com evidência forte; 0,85 caso contrário).
2. `existe` → **site_proprio** (0,7).
3. `bloqueado` com associação forte, ou `confirmado_trecho` → **site_proprio** (0,6).
4. Site da fonte `indisponivel` ou `estacionado` → **possivel_indisponivel** (0,6).
5. Candidato não resolvido (`so_nome`, `nao_corresponde`, `nao_conferido`, `erro`, ou domínio de e-mail sem site) → **inconclusiva**.
6. Sem provedor de busca → **inconclusiva**. Com menos consultas bem-sucedidas que `busca_min_consultas` (padrão 2) → **inconclusiva**.
7. Caso contrário:
   - **somente_redes**, se há presença associada;
   - senão, **nao_localizado**.

   Confiança: 0,35 + 0,15 × consultas (máximo 3), mais 0,05 cada para consulta de telefone, agregador lido e domínio provável testado. Teto de 0,9; nunca 1,0 sem confirmação humana.

### Ao gravar o resultado

- `_apply_auto_result` grava só as colunas automáticas.
- Se a classificação mudar e houver correção manual divergente, registra "DIVERGÊNCIA" no histórico.

## 6. Decisões tomadas (podem ser revistas com o usuário)

| Decisão | Motivo |
|---|---|
| Subdomínio de construtor de sites (Wix, Google Sites etc.) conta como **site encontrado** | não oferecer site a quem já mantém um |
| Rede/franquia (tag `brand` no OSM) fica fora da campanha até revisão | normalmente usa o site da marca |
| Telefone e e-mail do CNPJ têm aviso "pode ser do contador"; peso de contato × 0,7 | o cadastro costuma trazer dados do contador |
| Perfis encontrados só pela busca, com nome parecido, ficam como `nao_confirmado` e não contam como presença | regra "não associar por nome" |
| Instagram, Facebook e Maps não são lidos; o usuário cola o texto como material | exigem login ou proíbem robôs |
| O resumo do negócio é montado deterministicamente; o Ollama só extrai fatos e redige a mensagem | evitar invenção |
| Mensagem do Ollama que viola as regras é trocada pelo modelo padrão, com aviso | segurança |
| Aprovar mensagem exige classificação sem site (somente_redes ou nao_localizado) e nenhum bloqueio das regras | revisão humana obrigatória |
| A revisão do piloto vira correção manual com origem `piloto` | uma única fonte de verdade |
| A amostra do piloto inclui "somente redes" por padrão (desmarcável) | as duas classificações significam "site não localizado" |

## 8. Riscos e limitações conhecidas

- **Nunca testado com dados reais.** Pontos sensíveis:
  - formato real das respostas do Overpass e do SearXNG;
  - qualidade da extração do modelo Ollama;
  - páginas de Linktree, cujos links podem estar em JSON (há um regex para `"url":"…"`).
- A cobertura do OSM no DF é incompleta.
- Os prefixos CNAE dos segmentos são referência e precisam de revisão.
- Os códigos de município do entorno no arquivo do CNPJ exigem a tabela `Municipios` da Receita (`--municipios-arquivo`).
- Heurísticas que provavelmente precisam de ajuste após o piloto:
  - limiar de diretório (mais de 6 telefones);
  - padrões de domínio estacionado (só em páginas curtas);
  - `GENERIC_WORDS`;
  - pesos da confiança.
- Telefone que aparece só em imagem não é lido.
- `address_in_text` é simples demais para endereços de Brasília (ex.: "CLN 205 Bloco B").
- `JobManager` executa uma tarefa por vez, em memória; as tarefas se perdem se o servidor reiniciar.
- Não há CI no repositório.
